# Phase 1 — AI proxy usage limits

Local implementation, 2026-11-08. No hosted migration, function deployment, secret change or production data access occurred. Hosted AI remains **not ready to enable**.

## What changed

- Additive migration `20261108000017_ai_usage_limits.sql` creates an RLS-protected counter table and a service-role-only `ai_usage_reserve` RPC. Anonymous and authenticated roles cannot read, write or call it; the service role uses the RPC rather than direct table access. The function locks the shared bucket before the user bucket and decides both in one database transaction.
- After verifying Auth and `crm.manage` and validating the payload, the Edge Function reserves an attempt using the verified Auth user ID—not an ID or limits supplied in the request body. An exceeded limit returns 429. Missing/invalid configuration, database errors, unexpected RPC results and exceptions return 503 without calling the model. Each allowed provider attempt consumes quota, including provider failures and ambiguous network outcomes. Invalid/unauthorized requests do not consume quota.
- Both server-side settings are mandatory, with **no default quota**: `AI_AGENT_USER_LIMIT_10M` must be a positive integer up to 1,000, and `AI_AGENT_GLOBAL_LIMIT_24H` a positive integer up to 100,000. The first is per verified user in a 10-minute fixed window; the second is shared across users in a 24-hour fixed window. Windows start with the first allowed attempt and reset on the first allowed attempt after expiry. These maxima are validation ceilings, not suggested operating limits or an approved spending budget. The owner must choose operational limits before staging; no secrets or hosted settings were changed here.
- Request bodies are bounded to 32 KiB while streaming (even if Content-Length is absent or false), and to 10 messages. Existing per-message and grounding clipping and the provider's requested 320-token output limit remain. A provider may ignore requested output limits; input bytes are not token accounting.
- The inbox's offline draft remains separate. Settings now notes that attempt limits are not hosted-verified and that provider-budget, trusted-grounding and privacy controls remain open.

## Limits of this control

These are **attempt counts**, not monetary or token budgets. Fixed windows permit boundary bursts and do not cover other functions, clients, API keys, or direct provider usage. Old or parallel Edge Function versions can bypass the limiter or use different configured limits; coordinate versions and settings. The global database row serializes all reservations and could become a bottleneck. The limiter does not rate-limit unauthenticated Auth/RPC attempts. Provider-side budget controls, WAF protection, monitoring, alerting and operational ownership are still required. Failed or timed-out reservations may have committed in the database; this can consume quota without a provider call, which is the conservative behavior.

The table retains one shared bucket and one bucket per verified user UUID that requests a reservation; it does not contain message text, tokens, provider keys or monetary values. A denied call can create an empty user bucket. Agree retention, access and deletion policy before hosted rollout; no automated cleanup is included.

**Client-provided grounding is still untrusted, model output is not verified, and privacy/consent requirements are unresolved.** This slice does not make the hosted copilot safe for customer data or production use. No claim is made about provider billing or a hosted kill switch; for a deployed new function, missing quota configuration blocks provider calls, but it cannot disable any older deployed version.

## Staging and rollback

1. Do not enable hosted AI until independently approved trusted, versioned grounding, privacy/consent and provider budget controls are implemented. Identify existing deployed function revisions and all provider-key consumers. Choose small owner-approved staging limits and a provider-side budget cap; never place secrets in the browser, Git, logs or chat.
2. After approval and a verified backup/restore plan, apply migrations in order to an isolated staging database and deploy the matching function only to staging. Set both quota variables in the Edge Function's server environment and use synthetic users/data and staging provider credentials. Confirm real service-role-only grants, RLS, Auth/capability roles, 429 and 503 paths, configured and missing limits, body limits, reset boundaries, multiple users and **concurrent independent connections**, provider errors/timeouts and consistent configuration across revisions. Verify spend and alerting separately. Hosted tests are still outstanding.
3. Coordinate app/function and schema versions: the new function fails closed if migration `00017` is absent; applying the database alone does not protect an older function that never calls the RPC. Identify all other paths using the provider key.
4. To stop the **new** staging function, use an approved gateway/disablement procedure or remove its provider key/required limit settings; verify no old revisions or other services can still invoke the provider. A code rollback to the previous function would bypass the limiter, so keep it blocked or supply equivalent protections. Keep counter data until retention and rollback policy are approved; do not drop the table or rewrite production data as a quick rollback. If schema rollback is later needed, use a reviewed forward migration after all callers are stopped and verify dependencies, grants and retained data first.
