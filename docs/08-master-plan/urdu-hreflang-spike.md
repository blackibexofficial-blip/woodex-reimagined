# Urdu `hreflang` + string externalization — spike report (P3.5)

**Date:** 2026-11-06 · **Status:** evaluation only — nothing user-facing shipped · **Owner ask:** pick Option A / B / C below

## Verdict up front

Urdu support is **feasible but not a sprinkle of `<link rel="alternate">` tags**. The single biggest hidden cost is
**RTL layout** (Urdu is right-to-left; the whole Tailwind surface uses `left-*`/`pl-*`/`ml-*`/`text-left`/`items-start`
style logical-unaware utilities). Shipping hreflang *before* real `/ur/` pages exist would actively harm SEO —
`hreflang` URLs must resolve and must be content-equivalent. Recommendation: **Option C (defer)** for launch;
**Option B** if the owner wants a 2026 Q1 Urdu landing for B2B outreach.

## Measured inventory (storefront only — admin stays English-only, owner decision)

| Area | Size | Notes |
| --- | --- | --- |
| `src/pages` + `src/components` `.tsx` | 105 files | **~313 hardcoded JSX text nodes** (regex sample, excludes admin) |
| SEO metadata | `src/data/seoContent.ts` | `categorySeo` / `seriesSeo` SeoBlocks (title, description, intro, FAQ) for ~20 collections — translate wholesale, not per-page |
| Catalogue | `src/data/products.ts` (~2,950 lines) | product names/descriptions/specs for ~180 products; names stay Roman/English in trade by convention, descriptions need Urdu |
| `index.html` | static | `<html lang="en">`, `og:locale en_PK`, title/description/theme-color — the only file that sets document language today |
| Sitemap | `public/sitemap.xml` (generated by `scripts/generate-sitemap.ts`, 182 URLs) | the natural hreflang anchor — needs `xmlns:xhtml` + per-URL `<xhtml:link>` pairs; deterministic regeneration from data modules already works |
| i18n library | none installed | no react-i18next/lingui; `lang` never changes; routes have no locale prefix |
| JSON-LD | `seoContent.ts` | `inLanguage` not set anywhere (defaults en) — cheap win when /ur exists |

## Options

**A — Full Urdu storefront** (`/ur/…` locale routes on the same SPA, react-i18next or Lingui, translated
chrome + catalog + SEO + RTL audit). Effort **6–10 dev-weeks** + native-speaker translation pass on the catalog +
**RTL audit of all 105 files** (convert to logical properties or scope `dir="rtl"` with per-locale overrides) +
sitemap hreflang pairs + `og:locale:alternate ur_PK` + `inLanguage: "ur"` in JSON-LD. Highest ceiling, highest cost,
highest maintenance (every new string must ship in both locales from day one — enforce with a lint rule).

**B — Slim Urdu essentials** (chrome only: nav, footer, forms, checkout, CTAs, trust badges, ~40–60 strings via a
tiny hand-rolled dictionary + `/ur/…` shell rendering Urdu UI over the English catalog). Effort **2–3 weeks**
incl. RTL for the chrome only. hreflang **only** for the routes that genuinely exist in Urdu (`/ur`, `/ur/contact`,
`/ur/b2b`…) — never for untranslated product pages. Right size for "Urdu-first customer service, English-first catalog".

**C — Defer with groundwork** (recommended for launch): ship English-only; keep the three things that make A/B
cheap: (1) SEO strings stay centralized in `seoContent.ts`, (2) sitemap stays generated from data modules (it already
is), (3) new code keeps copy out of inline JSX where practical. Add **nothing** user-facing now — no `lang` flips,
no empty `/ur` stub, no hreflang to nowhere. Revisit after launch with real demand data (WhatsApp enquiry mix is the
best signal WOODEX already collects).

## What hreflang will look like once `/ur/` exists (for the record)

Per generated `<url>`: `<xhtml:link rel="alternate" hreflang="en-PK" href="{en url}"/>`, `ur-PK`, and
`x-default → en`; root `<urlset>` gains `xmlns:xhtml="http://www.w3.org/1999/xhtml"`. `index.html` gains
`<meta property="og:locale:alternate" content="ur_PK">` alongside `en_PK`; `<html lang>` becomes route-driven
(`en-PK` / `ur-PK`); every JSON-LD builder gains `inLanguage`. The sitemap generator change is mechanical (~30 lines)
and should ship **in the same commit** as the first real `/ur/` route — never before.

## Explicitly out of scope / non-goals (do not do these)

- No hreflang to untranslated URLs (Google drops both entries; worse than none).
- No machine translation shipped without native review — furniture/trade Urdu reads badly literal; brand damage > SEO gain.
- No `/ur` 404 stub for SEO bait. No `?lang=ur` query-param locale (splits canonical equity; use path prefix).
- Admin panel stays English-only (owner decision 2026-11-06).

## Decision needed from owner

1. A / B / C? 2. If A/B: who is the native Urdu reviewer, and is the catalog (~180 blurbs) in or out of translation scope?
3. Does the planned Bagisto provisioning change this (Bagisto has first-class locale fallback — the admin side is already out of scope either way)?
4. RTL: acceptable to convert layout to logical CSS properties incrementally behind a flag, or hard-scope `dir="rtl"` per locale?
