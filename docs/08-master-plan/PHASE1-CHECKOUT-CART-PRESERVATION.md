# Phase 1 — checkout cart preservation

Status: local, bounded mitigation, 2026-11-08. Not deployed and not included in PR #29. No hosted services, customer orders, real challenge provider or production data were accessed. This is not reliable idempotency or a synchronized multi-tab cart.

## Problem and behavior

The checkout captured its displayed cart for order submission but unconditionally cleared the then-current cart after confirmed success. If a shopper edited the cart during an in-flight order, the newly changed cart could be lost.

- The local CartProvider keeps an in-memory edit revision and a snapshot of the rendered basket. An edit requested in the same tick as submit also invalidates the older rendered snapshot. After Turnstile, but before invoking the order adapter, checkout compares the snapshot with the local revision and stored cart. A detected change or inaccessible/mismatching storage cancels the attempt **before any order call**, unlocks the button and asks the shopper to review (and refresh if needed). It does not mark this pre-order cancellation as an unknown order.
- Once the order call has started, success conditionally clears the cart only if the in-memory revision, current rendered items and the stored basket still match that snapshot. A same-tab edit, including an edit that was later reverted, keeps the whole cart. A detected other-tab storage change also prevents this particular clear; nothing attempts to subtract the ordered quantities. On a successful order, a note warns that a changed cart may still contain ordered items and should be reviewed before ordering again. Existing uncertain outcomes continue to retain the cart and require acknowledgement before retry.
- Cart data is not copied to a new persistent storage key; snapshots are in memory only. Existing URLs, the manual clear-cart control and the normal unchanged-cart success path remain in place.

## Limitations and risks

- **No atomic cross-tab safety.** Browser storage is read separately from React state updates and their later storage write; another tab can change it between the check and write. The cart does not synchronize storage events, and other tabs have independent stale state that can overwrite one another during ordinary edits or mount. A different stored value at one checked moment is only detected, not merged into the active tab. Refresh to see stored data when appropriate, but even refresh cannot resolve competing writes. Independent multi-tab testing and a deliberate cart concurrency design are still needed.
- Keeping the *whole* changed cart can leave already-ordered items in it; the success note asks users to review before another order. The displayed success still uses the adapter's prior success semantics. Bagisto outcomes remain unconfirmed. No server-side check binds the cart to its order or verifies current prices, and no stock, order, payment or downstream delivery guarantees are added.
- Form fields, pricing/session data and other tabs are not frozen or synchronized by the snapshot; it covers cart items only. React/browser lifecycle, reload, navigation, race conditions and direct API clients remain outside this guard. A hung request can remain pending; on an ambiguous failure or lost response, duplicate-order risk remains. See `PHASE1-CHECKOUT-RETRY-SAFETY.md` and `PHASE1-BAGISTO-ORDER-OUTCOME.md`.
- If storage cannot be read or is out of sync at the post-verification check, checkout conservatively stops rather than sending; if it differs after submission the cart stays. Existing `localStorage` write handling is unchanged. Real browser private-mode, quota and multi-tab conflict recovery have not been comprehensively tested.
- The site contact details and delivery promises remain owner-unverified. None of these tests validates a real challenge token, network, hosted Supabase schema/permissions, Bagisto endpoint, payment, or actual database concurrency. Release requires the separate staging and owner approvals in the checklist.

## Evidence

- `WOODEX_TEST_BASE=http://127.0.0.1:8083 npm run test:checkout-cart-preservation`: **9/9** local browser checks. Mocked pending demo order covers same-tick edit, unchanged cart clearing, quantity change after send, original submitted quantity, edit-and-revert, a second page changing shared storage before success, warning text and browser errors. The two-page case demonstrates one observed ordering of events, not a concurrent-storage proof.
- Demo `test:checkout-safety` **10/10**, mocked Supabase `test:checkout-challenge` **5/5** (including edit during pending fake challenge with no order sent and retry with a fresh token/current cart), mocked Bagisto `test:bagisto-order-outcome` **18/18**, and demo E2E **108/108**. External requests were blocked in the browser tests and test servers used synthetic keys only.
- Typecheck and build passed; lint passed with **35 existing warnings**, and build reports stale Browserslist data and large chunks. One earlier challenge-test run timed out when a transient toast overlapped the submit button; waiting for its dismissal produced the recorded pass. Chromium's single-process configuration could not create an incognito browser context, so the new test uses ordinary pages with synthetic data instead; no production connection was involved.
- Browser test servers: demo mode on port 8083 with fake Supabase configuration, Supabase fake challenge mode on 8081 using `https://checkout-test.invalid` and synthetic keys, Bagisto mode on 8082 using a local fake endpoint. Start fresh before tests which monkey-patch Vite modules; stop after testing. The production-build E2E used temporary Bun via `npm exec --yes --package=bun -- npm run e2e`.

## Before release

Owner must verify support contact and the cart/retry experience. Review the actual backend and independent-tab behavior on isolated, access-controlled staging with synthetic data; reproduce a response lost after commit, simultaneous edits, storage unavailable/quota, checkout from a stale tab, navigation/reload, and pricing/session changes. Design atomic cart revisioning/conflict handling and a server-authorized, payload-bound order retry/recovery contract before claiming this is safe across tabs or reliable against duplicates. Do not deploy or modify hosted data without explicit authorization.
