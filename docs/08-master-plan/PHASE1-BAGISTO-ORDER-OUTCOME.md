# Phase 1 — Bagisto order outcome honesty

Status: implemented locally and tested with synthetic requests, 2026-11-08. **Not deployed, not included in PR #29, not a verified Bagisto integration or complete retry solution.** No real Bagisto endpoint, production order, hosted database or provider was accessed.

## Finding and bounded change

The Bagisto `createOrder` adapter uses an unverified single-shot `POST /api/shop/checkout`; it discarded the response and returned a fabricated browser-local `WDX-WEB-*` order on both 2xx and caught failure. Its fallback wrote customer and order details to localStorage, swallowed storage errors and had no automatic delivery worker in this application. Checkout and manual admin order screens could claim success, clear the cart or navigate to a printable order that might not exist remotely.

- The adapter now returns transient `submissionOutcome` metadata: `bagisto-response-unverified` for a parsed 2xx response, `bagisto-queued-locally` only if the fallback write succeeded, and `bagisto-not-saved` if it failed. A 2xx JSON body is deliberately **not** treated as a confirmed order or its generated local ID as a remote receipt. A malformed/empty 2xx body goes through the failure/fallback path because the existing request helper parses JSON. Neither a successful local write nor any response is proof of a remote order.
- Storefront checkout retains the cart, shows the appropriate local/unverified detail alongside the existing possible-duplicate warning and requires explicit acknowledgement before another attempt. It does not display the fabricated ID or success screen for these outcomes. The local-copy notice also identifies that contact/order data were stored in the browser and that this app does not automatically send them to the team.
- Manual admin order entry similarly remains on the form, avoids the fake print URL and asks staff to reconcile and acknowledge duplicate risk before retrying. Adapter exceptions are conservatively uncertain, including definite failures. The shared manual order/invoice form now uses a synchronous in-flight lock to guard same-tick clicks. Ordinary demo orders still navigate to their print view.
- The order fallback format and `woodex.outbox.orders.v1` key are retained, with no automatic replay and no changes to hosted data. `outboxPush` now returns whether storage succeeded. A later local follow-up uses it for lead outcome warnings; see `PHASE1-LEAD-OUTCOME-SAFETY.md`. Lead delivery and durability remain unresolved.

## Limits, privacy and release gates

- A Bagisto 2xx may actually mean success, failure or a different checkout-flow step. This implementation intentionally marks **every** Bagisto result unconfirmed until the instance's actual API and response mapping are verified. Manual reconciliation is required; do not fulfil, resend or charge based on local status. The unverified endpoint may already have committed even after a network error, malformed response or storage failure.
- The browser-local fallback can be blocked, cleared, lost or read by other users/scripts with origin access; it contains personal and order data. There is no built-in staff inbox, automatic delivery, privacy/retention policy, stable retry identity or reliable customer recovery mechanism. Existing outbox entries were not inspected, migrated or deleted. Review exposure, retention, consent and handling of old entries before real use. The site phone is a placeholder/consolidated value requiring owner confirmation.
- The lock/warning lasts only for the mounted page; reload, navigation, other tabs or clients bypass it, and explicit retries can create duplicates. In-flight requests can hang. Shared-browser cart/outbox state is not server truth. All outcomes are not classified as definitive failures, by design.
- Review Bagisto's real version, checkout token flow, success/error contract, authentication, order reference and server-side verification on isolated staging; decide a durable, secure staff reconciliation/outbox workflow and idempotency contract; test independent concurrent requests, lost responses, rollback and inventory. Confirm real support procedures and never place real orders during testing. Shipping any Bagisto admin token in a public frontend remains unsafe. No hosted rollout or real-money use is approved here.
- At this slice, lead callers still reported a local lead even when the outbox write failed. A later local UI/adapter mitigation is documented in `PHASE1-LEAD-OUTCOME-SAFETY.md`; neither slice establishes reliable delivery.
