# Phase 1 — CMS storefront snapshot boundary (in progress)

## Scope and status

An **opt-in staging-only** `/p/:slug` route now exercises the published snapshot renderer. It is off by default (`VITE_CMS_STOREFRONT_PREVIEW=0`); the existing homepage, other storefront URLs and `/lab/:slug` are unchanged. This flag is not authentication and enabling it on a publicly reachable host exposes published content. The change remains local and uncommitted; no hosted migration, deployment or production data change was performed. B3 (CMS-to-storefront publishing) remains incomplete.

`20261108000020_storefront_snapshot_boundary.sql` adds `storefront_page_snapshot(text)`. It reads only the stored published snapshot, requires the current row to be published and of kind `page`, excludes `chrome`, and looks up the **published** slug rather than a subsequently edited draft slug. It projects the snapshot's id, slug, title, publication time, theme, blocks and selected SEO fields; top-level unknown fields, non-public SEO controls and extra block wrapper fields are omitted. Block order is retained. Missing, ambiguous and structurally invalid snapshots return null, including multiple published pages claiming the same published slug. Explicit boolean `noindex` is preserved; a malformed value defaults to noindex. Existing `published_page` and preview behavior remain unchanged.

Anon and authenticated roles can call the new RPC; neither obtains draft data from it, including authenticated editors. A restore changes the draft, not the live Supabase snapshot; republishing is required to make it live. The demo adapter behaves differently: restore sets the page to draft and makes it unavailable until republished. New demo publish revisions now capture slug, title, document, SEO and publication time together. The reader uses only a complete revision matching the current published version and timestamp, never current draft fields; old revisions without slug/SEO (including the seed) need an explicit republish. Duplicate published slugs fail closed. Demo data remains per-browser, not a shared production publishing system.

## Frontend snapshot reader

`src/api/storefront-pages.ts` exposes `getStorefrontPageSnapshot(slug)` for a future renderer. In Supabase mode it calls only the new published RPC and validates/project its response; it never queries admin page rows or falls back to `getPage`. Demo mode reads the captured publish revision. A missing or ambiguous result is `undefined`; backend/configuration errors and invalid client payloads are typed errors. The SQL function itself returns null for both missing and some malformed snapshots, so callers cannot distinguish those cases from a genuine 404 solely via the RPC. A future route must handle unavailable separately and avoid caching a backend error as a missing page. SEO noindex defaults safely to true for malformed values; focus keyphrases and strict-gate controls are not returned. Props and theme remain public and untrusted.

## Provisional public-document preflight

`src/pages-builder/public-document.ts` validates a narrow profile and, on success, returns a new document copy. `src/pages-builder/storefront-source.ts` combines the published-only reader and preflight: missing content returns absent, backend errors remain errors, and unsupported published documents raise a distinct error. The opt-in staging route uses the returned validated copy rather than the raw snapshot, retains public builder mode, and handles missing, unsupported and backend errors without draft fallback. Any future production renderer must preserve those boundaries. This is a client-side rendering boundary, not server-side authorization or a replacement for the published RPC.

The initial profile allows only 13 simple blocks: Heading, SubHeading, Paragraph, SmallLabel, SectionHeading, ButtonLink, Button, TwoButtons, Spacer, DividerLine, HeroCentered, HeroCenteredTrust and CtaStrip. It enforces valid unique IDs, known string fields and enum values, URL guard checks, 50 blocks, 4,000 characters per field and 100,000 characters total. Unknown/extra fields, additional Puck zones, malformed structures, nonempty linked styles or block inspector styles, formatted HTML in rich-text fields, image/embed/form blocks and unknown blocks reject the **entire** document, including hidden blocks. Existing and seeded pages may therefore fail this limited profile. It does not review the truth of content, prevent phishing through permitted links, make hidden content private, or constitute an independent security/accessibility certification. The full builder remains available in the editor and LAB.

The editor displays an **advisory check of the current editor content**, including potentially unsaved edits. It does not inspect the published revision and does not block saving or publishing; a passing result does not mean a public URL exists, that the content has been published, or that it is approved for release. The eventual server/public-render deployment still requires staging, content/security and accessibility review.

## Important limitations and release gates

- This projection is not an HTML, link, CSS, embed, or content sanitizer. All block `props` and the snapshot `theme` are publicly returned, **including hidden block contents** and any sensitive material an editor puts there. Hidden is a visual setting, not confidentiality. Editors must publish only public information. Already-published snapshots were already accessible through `published_page`; this new endpoint is not a substitute for reviewing that existing endpoint and exposure.
- The five demo form blocks (`HeroForm`, `HeroSplitForm`, `EnquiryForm`, `CallbackForm`, `NewsletterSignup`) now fail safe in the new public builder mode: no form is rendered; visitors see an unavailable notice, with a link to the existing contact page for enquiries (not for newsletters). No lead or newsletter integration was added or verified. The editor and LAB explicitly retain the forms, with a visible preview-only warning and truthful no-submission alerts. Public mode is the context default; LAB and editor opt into preview/editor modes. The fallback is not a substitute for a real approved submission flow.
- Configurable builder links and rich-text anchors now reject executable/unsupported schemes, control characters, backslashes, protocol-relative URLs, and credentialed web URLs; ordinary relative/http(s)/mailto/tel links remain. Invalid links have no href. This does not prevent phishing on permitted external sites or sanitize image URLs, styles, embeds or all possible HTML. The legacy rich-text sanitizer remains custom and requires independent security review. Review image URLs, inspector styles, external embeds, block schemas, malformed/unknown component handling, accessibility, and third-party/privacy behavior before any public route.
- The opt-in staging namespace is `/p/:slug` (lowercase ASCII letters/digits separated by single hyphens; max 128 characters). Existing top-level routes and `/` remain unchanged. This SPA renders status messages but does not set HTTP 404/503 codes; the host may return 200 for missing/failed routes. It sets a staging-origin canonical and `noindex,nofollow` **in the browser only**, with a visible preview banner. Initial HTML, social crawlers, server headers, server rendering, caching, sitemap, redirects and production SEO are not implemented or verified. Require host-level `X-Robots-Tag: noindex, nofollow` and restricted staging access; JS noindex is not sufficient protection.
- Published slug collisions fail closed for this new RPC; publication itself does **not** prevent collisions. They can arise if a page's draft slug changes and another page takes its old published slug. Editorial error reporting and transactional collision prevention are outstanding. Current `kind` is not captured in historical snapshots and is checked on the row; changing it can affect eligibility without publishing. Direct privileged table writes remain possible.
- Already-open pages are not polled or invalidated on publish/unpublish; users see a prior public snapshot until navigation or reload. Revocation, edge caching and real-time refresh need an explicit deployment design.
- Existing demo localStorage entries with no complete publish revision cannot safely be inferred from the current editable document; require an explicit republish. Demo storage is per browser and its localStorage persistence is best effort; it is not a security boundary or a shared production publishing system. The static and Bagisto modes have no supported reader and report unavailable rather than falling back to demo data.
- Existing anonymous `/lab` preview falls back to the older public snapshot RPC; authenticated editor preview reads drafts. The new boundary does not change or certify `/lab` access controls.

## Opt-in staging route

`VITE_CMS_STOREFRONT_PREVIEW=1` enables the lazy `/p/:slug` route in a **new build or dev server**. Never enable it in production without owner approval, security review and staging verification. It is a feature flag, not an access control; restrict the staging host at the infrastructure layer and send `X-Robots-Tag: noindex, nofollow` on the initial response. Treat all published block props and themes as public, even when a block is visually hidden.

The route calls only `getRenderableStorefrontPage`, which reads the published projection and validates the 13-block profile. It renders a published snapshot inside normal storefront header/footer, always shows a staging banner, and separates loading, missing/ambiguous, unsupported, transport/invalid-payload and rendering-failure states. It does not display internal errors or fall back to drafts. Navigation invalidates stale async results; the current snapshot is not live-updated. It does not perform SSR, issue status codes, or establish a production CMS route. Demo and Supabase restore behavior remains different as described above; static/Bagisto mode is unsupported. Reverting the flag to 0 and rebuilding disables this route without changing existing pages or database rows.

## Staging and rollback

After owner review and backup, audit existing published snapshot schemas, duplicate published slugs and exposed block/theme content in staging. Apply migrations in order only in staging; verify anonymous and authenticated RPC calls through real PostgREST, deny draft/raw-table access, exercise publish/edit/restore/unpublish and duplicate cases, and verify existing preview paths. Do not enable the route on production, or any unrestricted staging host, before the release gates above are resolved. Roll back this standalone unused endpoint with `drop function if exists public.storefront_page_snapshot(text);` after confirming no consumer depends on it. This does not reverse preceding Phase 1 migrations or alter page content.
