# Phase 1 — lead outcome safety (bounded local mitigation)

Status: implemented and locally tested, 2026-11-08. **Not deployed, not in PR #29, not proof of reliable enquiry delivery.** No real Bagisto, Supabase, Cloudflare, production records or hosted service were contacted.

## Findings and changes

- Bagisto's custom lead endpoint previously discarded its response and returned a generated local lead for 2xx, network error and even failed localStorage writes. Contact, quote and offline-chat forms could report delivery or promise a callback despite no verified remote receipt. The browser-local `woodex.outbox.leads.v1` is not automatically delivered by this app.
- The Bagisto lead path now returns transient outcome metadata: a parsed 2xx is **unverified**, a failed HTTP/parse attempt with successful storage is **browser-only**, and a failed storage write is **not saved locally**. The original outbox key and contents are retained. Offline chat uses the same lead path and carries the outcome through; no fabricated chat ID is stored as a thread when unconfirmed. These statuses do not prove whether a remote write did or did not occur.
- Contact, quotation and offline chat keep entered details on uncertain outcomes, show an accessible warning with the browser storage/delivery distinction when applicable, and require acknowledgement of possible duplicates before retry. A synchronous page-local lock prevents overlapping submits, and form fields/consent are disabled while a request or challenge is underway. Errors are conservatively uncertain; pre-submission challenge failures are treated separately and unlock the form. No retry is automatic.
- Offline chat previously called Supabase lead capture without a Turnstile token. It now requests a `lead` token before calling the adapter and passes it through to the existing `lead-capture` request. A challenge failure does not submit a lead. Demo/Bagisto mode do not enable the Supabase challenge. Configuring Cloudflare, enforcement and hosted behavior remain separate release gates.
- At this slice the Supabase adapter required a response with `ok: true` and a positive numeric ID (safe integer or decimal string) before presenting a lead as captured. A later local follow-up additionally requires a v2 acknowledgement and modifies the Edge Function; see `PHASE1-LEAD-CONTENT-CONTRACT.md`. Missing, malformed or unverified receipts are uncertain rather than fabricated success. A valid receipt is not evidence of later staff follow-up.

## Verification

- `npm run test:bagisto-lead-outcome`: **15/15** browser checks against the real local adapter and UI with intercepted synthetic responses. Tests 2xx, 500, network failure, invalid JSON, local storage denial, consent denial without request, same-tick double submission, contact/quote/chat unconfirmed UI, acknowledgement, form/quote-basket retention and no fake chat thread. All external network was blocked.
- `npm run test:supabase-lead-challenge`: **11/11** browser checks using the actual frontend adapter and a fake challenge/HTTP endpoint. Tests in-flight lock and disabled inputs, failure before send, chat token propagation, invalid/missing receipt, 403, quote success, numeric-string receipt and no uncaught errors. It does **not** test Cloudflare, hosted Auth or the real Edge Function.
- `npm run test:demo-lead-safety`: **7/7** browser checks with a mocked ambiguous error and unmocked browser-local demo contact/quote submissions. External network blocked. Existing tests rerun: Bagisto order outcome **18/18**, checkout safety **10/10**, manual order safety **5/5**, checkout challenge **4/4**, intake helper tests **24/24**, and mocked actual-handler Deno tests **2/2** (no network permission). The checkout-challenge test initially missed its adapter mock after the development server had hot-reloaded the adapter and got a local 404; after restarting the test server it passed. Tests that monkey-patch Vite modules should run against a freshly started server.
- The built demo regression suite passed **108/108** when run in isolation. An earlier concurrent run timed out waiting for the page while other browser tests were active; no cause was conclusively established. The successful run preceded the final Supabase receipt-ID validation tightening; the final Supabase-specific browser suite and subsequent build passed after that change.
- `npm run typecheck`, `npm run lint` (35 existing warnings), and `npm exec --yes --package=bun -- npm run build` passed; build warns about large chunks and stale Browserslist data. No hosted or real-provider integration was tested.

## Running synthetic browser tests

Use a demo server on 8080 for `test:demo-lead-safety`. For `test:bagisto-lead-outcome`, start an isolated Vite server on 8082 with `VITE_API_MODE=bagisto VITE_BAGISTO_API_URL=http://127.0.0.1:8082 VITE_BAGISTO_STOREFRONT_KEY=fake-local-key`. For `test:supabase-lead-challenge`, use an isolated Vite server on 8081 with `VITE_API_MODE=supabase VITE_SUPABASE_URL=http://127.0.0.1:8081 VITE_SUPABASE_PUBLISHABLE_KEY=fake-local-key VITE_TURNSTILE_SITE_KEY=fake-local-site-key`. Each test intercepts mock API calls and blocks external requests. Never use real keys; stop test servers afterward. Browser-local test identities are not authentication.

## Open risks and release gates

- All current Bagisto lead responses, including 2xx, remain unconfirmed until its specific custom endpoint and response contract are reviewed and tested on isolated staging. This mitigation warns; it does not create a staff inbox, reliable queue, automatic delivery, reconciliation workflow or idempotency. Network failures, invalid responses, or storage failure can occur after a server commits. Acknowledged resubmission can duplicate records. Warnings and locks do not survive navigation/reload, other tabs or direct API clients. Requests can hang indefinitely.
- Existing browser-local lead outbox entries contain personal and enquiry details; shared devices, scripts, storage clearing or quota affect privacy and durability. No old data was accessed or deleted. Owner must decide retention, consent, secure recovery, duplicate handling and operational deletion before real use. Do not tell customers that a local copy reached staff. Verify the configured contact number before release; it is flagged for owner confirmation in `src/config/site.ts`.
- Supabase strict intake policy remains opt-in and undeployed. Real challenge action, secret/site-key pairing, proxy behavior, rate limiting, real Edge/DB grants and error contracts require authorized staging tests. Valid response shape does not prove real callback delivery. Lead records do not have a complete retry identity contract; hosted live chat remains unavailable. A later local versioned capture contract reduces truncation for upgraded clients, but older clients still truncate and structured quote requests remain incomplete; see `PHASE1-LEAD-CONTENT-CONTRACT.md`.
- Test independent clients/concurrency, committed-but-lost responses, storage denial, reload/multi-tab, consent changes, real challenge/provider errors and staff reconciliation with synthetic data only on explicitly approved staging. Verify supported Bagisto versions and security. No release authorization follows from this report.
