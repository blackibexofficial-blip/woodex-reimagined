# Phase 1 — checkout retry safety (bounded local mitigation)

Status: implemented and locally tested, 2026-11-08. **Not full idempotency, not deployed, and not in PR #29.** No hosted services, production orders, providers or databases were contacted.

## What changed

- Checkout takes a synchronous, component-local lock before starting the Turnstile challenge, blocking overlapping submit events even before React renders the disabled button. A challenge failure unlocks it without sending an order.
- If the adapter throws after order submission starts, the page no longer asserts that no order was placed. It keeps the cart, displays an ongoing warning, and requires an explicit acknowledgement of duplicate risk before another submission. Each subsequent error requires a new acknowledgement. No retry is automatic. The configured site phone is used; **the owner must verify it before release**, because `src/config/site.ts` flags the consolidated contact details for confirmation.
- At the time of this slice, a returned order used the existing confirmation and cart clearing and no adapter was changed. **Follow-up:** `PHASE1-BAGISTO-ORDER-OUTCOME.md` records a later local change that tags Bagisto's unverified responses and local fallback, retaining the cart and warning rather than presenting those outcomes as confirmed. No hosted configuration was changed.

## What this does NOT solve

- The lock and warning exist only for the mounted checkout component. Reload, navigation, another tab or browser, a direct API client and browser crashes bypass them. Explicit acknowledgement allows a retry and may create a duplicate. The Supabase adapter still generates a new `clientRef` for every call. No stable attempt key or customer data was added to browser storage. An in-flight request has no client-side timeout; a hung request can leave the button disabled. A later local follow-up conditionally retains a changed cart after success and checks again after verification; this is not atomic cross-tab protection. See `PHASE1-CHECKOUT-CART-PRESERVATION.md`.
- All adapter errors are conservatively shown as uncertain, including definite validation or rejection errors; this may unnecessarily direct customers to support. Verification failures before `createOrder` are handled separately. The cart is not proof the order failed.
- Existing SQL looks up `client_ref` without binding it to the request payload, and the receipt projection still exposes item and total information for a known reference. The partial unique index alone does not authorize replay or specify outcomes for concurrent identical requests. A reference is potentially bearer-like and must not be treated as authentication. The RPC's rate limiter runs before replay; transactional errors, challenge-token reuse, stock updates, privacy, and concurrent retries require explicit end-to-end design and verification. Merely saving and reusing the current reference would not make this safe.
- The Bagisto outbox/remote success semantics and demo behavior are distinct from Supabase. Do not apply a Supabase-specific retry contract to them without reviewing integration semantics. Do not infer payment settlement from checkout success.

These checks are not hosted verification or independent-connection concurrency tests.

## Before claiming reliable retries

1. Decide the backend-specific checkout/outbox contract and a safe recovery experience for lost responses, reloads, multiple tabs, edited carts/forms, expiration, and cases requiring manual reconciliation. Confirm the actual customer-support number and procedure.
2. Design and security-review a server-controlled, high-entropy attempt/recovery credential and strictly defined canonical request binding; consider retention, storage, authorization and replay response minimization. Reject same-key/different-payload safely without exposing another order. Define behavior for old clients and existing references. Do not store sensitive customer data or bearer-like credentials casually in localStorage, logs, URLs or analytics.
3. Define atomic reservation/creation/replay behavior under independent simultaneous Postgres transactions, including failures before/after commit, stock and event rollback, ordering/deadlocks, rate limits and fresh Turnstile tokens. Review policies and service-role-only grants with existing hosted schema before any migration.
4. Add deterministic unit and actual-handler tests plus independent-connection real Postgres/staging tests: matching/mismatched replays, concurrent same-key requests, different keys competing for stock, rollback, timed-out committed requests, challenge failures, rate limits, authorization and receipt privacy. Exercise navigation/reload and separate tabs, and preserve legacy behavior deliberately.
5. Only after explicit staging authorization, run synthetic end-to-end verification, operational reconciliation, owner/security review, and a rollback rehearsal. No release approval follows from this document.
