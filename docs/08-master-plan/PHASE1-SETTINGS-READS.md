# Phase 1 — store settings read isolation

Local implementation, 2026-11-08. No hosted database, deployment, or production records were changed. The open pull request does not automatically include uncommitted local work.

## Scope and policy

Additive migration `20261108000019_settings_read_projection.sql` restricts raw `app_settings` SELECT to owners, retaining the existing owner-only write policy. Owner, editor, sales and finance can call `staff_store_settings()` according to the existing `page.manage`, `crm.manage` or `finance.manage` capabilities; viewer, unassigned and anonymous callers cannot. Owners receive the complete existing `store` object so previously stored unknown fields remain available to them. Other staff receive only typed store profile fields used by Settings and printable documents: store name, tagline, contact/address fields, currency, delivery note, tax rate and logo. Only CRM-capable staff receive the lead-assignee roster and offline-AI preference; non-string roster entries and wrong-typed values are omitted. Other settings rows, unknown keys, and nested objects inside allowlisted scalar fields are not included in the projection.

The allowlist and role choices are provisional and require owner review. Allowed string fields can themselves contain private content; this does not guarantee their contents are suitable for staff. The owner still has raw access to all `app_settings` rows under existing policy. This is a staff projection, **not a public settings API**. No existing data is rewritten by the migration.

The Supabase adapter reads through the new projection. The Settings screen is read-only for non-owners in Supabase mode, clears prior settings during session/permission changes, and displays read failures rather than an indefinite spinner. Browser permission checks are presentation only; the database remains authoritative. Demo and Bagisto behavior otherwise remains unchanged.

`owner_save_store_settings()` checks owner status, locks the store row and merges only recognized typed UI fields into the existing object. Unknown and omitted keys are preserved; unknown input keys are ignored. A deliberate null `storeLogo` removes that field, supporting the existing Remove logo control. This protects unknown fields when an owner saves a partial staff projection, but **does not** prevent stale overwrites of known fields: concurrent edits are last-writer-wins. It does not prevent authorized owners or legacy callers from using the existing raw table write policy. If other clients depend on saving arbitrary untyped keys via the adapter, they must be reviewed before rollout.

## Staging and rollback

1. Obtain owner approval for the per-role field allowlist and inspect the real contents of allowed fields, existing settings keys, writers, grants, extra permissive policies and function ownership. Do not assume the local migration history matches production. Agree how unknown fields and other clients are managed; back up and verify restoration before any hosted change.
2. On an isolated staging project only, apply the reviewed migrations in order and deploy the matching frontend. With synthetic records, test anonymous, unassigned, viewer, editor, sales, finance, owner and service role; raw reads, every projection and malformed/nested input; owner saves, logo removal and unknown-key preservation; documents, leads and inbox; revocation, independent concurrent owners and legacy callers. Regenerate and compare Supabase types. Verify actual PostgREST security-definer/RLS semantics and any additional permissive policies.
3. Coordinate releases: the new app needs both new RPCs; an older app may see no settings for non-owners or continue using destructive raw upserts. Deploying only the app fails closed if the RPCs are absent; deploying only the schema does not automatically fix old clients. Do not enable production without a separate decision.
4. Do not blindly restore broad authenticated SELECT. If rollback is necessary, use an approved equivalent security restriction, then a reviewed forward migration restoring specific prior policies/functions from a verified schema backup and coordinating frontend versions. Preserve existing settings; do not replace production blobs or restore a full database merely to undo this change.
