# Phase 1 — bounded enquiry details and capture contract

Status: local implementation and synthetic tests only, 2026-11-08. **Not deployed or in PR #29; not a complete structured quotation or production release.** No hosted database, real customer, Cloudflare or Bagisto endpoint was accessed or modified. No migration was applied.

## Problem and change

Previously the contact page cut its message to 180 characters, offline chat cut its lead summary to 160, and Supabase `lead-capture` cut `interest` to 120 while discarding company. Quote requests summarized only the first six basket lines, and the UI implied the basket was fully included. Admin leads showed summaries mostly as a two-line clamp.

- Local contact, quotation and offline-chat forms now send bounded full text rather than those silent client-side cuts. Contact message is limited to 3,000 UTF-16 code units and subject to 120; offline chat message to 2,000; quote project type to 500 and company to 160. Inputs display relevant limits/guidance. A quote snapshot is explicitly **plain text**, including all current line names, quantities, an available variant label or color, and an unconfirmed displayed estimate. If the combined summary exceeds 4,000 code units, the form blocks submission before verification/network and asks for fewer items or shorter text; it does not silently drop lines. The button now says “Submit Quote Request,” not “Download Quote.” The basket remains available for existing print/email/WhatsApp actions.
- Supabase capture uses an opt-in `capture_version: 2`: the function validates a non-empty interest of at most 4,000 UTF-16 code units and an optional company of at most 160; it writes them to the existing `leads.interest` and `leads.company` columns and compares returned values before emitting a version-2 acknowledgement. It does not echo those details in the public receipt. If verification fails after insert, it returns an error even though a lead **may already have committed**. The frontend requires both a valid ID and the v2 acknowledgement; an old deployed function's legacy success is treated as uncertain, not proof the full details were stored.
- Old callers without `capture_version` keep the existing 120-character clipping, no company write, and the old response shape. Unknown explicit versions fail. This backward compatibility prevents an unreviewed breaking change but **does not repair legacy or already-truncated leads**. The Supabase version marker covers only the bounded interest/company contract—not all submitted metadata or downstream processing.
- The lead details dialog displays the complete stored summary as scrollable, escaped text rather than relying on a truncated preview or a hover title. Demo offline-chat lead summary also retains the submitted message; browser-mode chat input is limited to the demo thread's 2,000-character bound.
- Because user-supplied company is now persisted by v2 and can appear in spreadsheet exports, the shared CSV exporter prefixes formula-like text (including leading whitespace/control characters) with an apostrophe before CSV quoting. This applies to lead, client and import-issue exports. Numeric values passed as numbers remain numeric; negative-looking strings are intentionally exported as text. This is a defense-in-depth change, **not a guarantee across spreadsheet versions, import settings or re-saved files**. Test the target applications before relying on it.

## Limits and release gates

1. Explicit owner/privacy approval is required before deployment: v2 retains **more customer-supplied text** and company data than before. Audit the real leads table, RLS, existing permissive policies, staff roles, logs, backups, deletion/retention and any triggers or consumers. The service-role insert and returned columns must work in the actual schema. Do not inspect or alter production records as a test.
2. Coordinate Edge and frontend versions. New Edge first preserves older clients' legacy behavior; old Edge with new frontend may already insert a clipped record but returns no v2 marker, so the UI warns of an uncertain result and staff must reconcile before retry. Browser caches, stale tabs, rollback, partial deployments, triggers and older integrations must be rehearsed on isolated staging with synthetic data. Never automatically retry an uncertain insert. Rollback must not silently reintroduce false confirmation.
3. The quote remains a **text snapshot**; product IDs, all options, authoritative line prices, city, actual structured totals, acceptance, and lead-to-quote linkage are not guaranteed or implemented. The Supabase function still ignores some client metadata such as `type`, `city` and numeric `value`; contact fields retain their existing bounds. Some messages may be rejected because the snapshot is too long. Hosted live chat remains unwired. Existing leads cannot be reconstructed from this change.
4. The warning/lock is page-local and not idempotency. Duplicate sends, response loss, external direct clients, stale tabs and unrelated backend errors remain open. Strict intake remains opt-in and undeployed; WAF/trusted proxy, budgets, real challenge action and hosted permissions require separate review. Bagisto's endpoint/response and browser-local fallback are still unverified and not automatically delivered.
5. Validate CSV exports with the owner's actual spreadsheet applications and workflows, particularly re-import/re-save, formula interpretation, delimiter/locale and leading controls; do not open untrusted CSVs as a production readiness test. No spreadsheet execution was tested here. Before any staging work, confirm access isolation, synthetic-only data, backup/restore, incident ownership and an approved rollback plan. Nothing here authorizes production use.
