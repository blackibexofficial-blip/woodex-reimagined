# Deploying Woodex OS v1.0.0

Everything here assumes you have unzipped the archive and are inside the
`woodex-v1.0.0` folder.

The one rule that causes 90% of failed installs: **the web root must be
`public/`**, not the folder that contains it. If you can browse to
`https://yourdomain.com/.env` you have pointed it one level too high — fix that
before anything else.

---

## 1. Requirements

| | |
|---|---|
| PHP | **8.4.1+** — this is a hard requirement, not a suggestion |
| Extensions | `pdo_sqlite` (or `pdo_mysql`), `mbstring`, `openssl`, `fileinfo`, `curl`, `json`, `tokenizer`, `xml`, `ctype`, `bcmath`, `gd` or `imagick` |
| Web server | Apache with `mod_rewrite` + `AllowOverride All`, or Nginx |
| HTTPS | Required in production — `.env.example` sets `SESSION_SECURE_COOKIE=true` |
| Disk | ~400 MB (uploads and logs grow from there) |
| Composer / Node | **Not needed.** `vendor/` and the compiled assets are included. |

Check your PHP version before you start:

```sh
php -v          # must report 8.4.1 or higher
```

If your host only offers 8.3, the archive will not run. Ask the host to enable
8.4, or use a different plan. Do not try to work around it.

## 2. Hostinger (shared hosting — the target setup)

1. **Upload.** hPanel → *Files → File Manager* → open your domain's folder →
   upload `woodex-v1.0.0.zip` → right-click → **Extract**. You can delete the
   zip afterwards.
   *(Or via SSH: `unzip woodex-v1.0.0.zip`.)*

2. **Set PHP 8.4.** hPanel → *Advanced → PHP Configuration* → choose **8.4**.
   Then in *PHP Options* confirm `pdo_sqlite`, `mbstring`, `gd`, `fileinfo`,
   `bcmath` are enabled.

3. **Point the web root at `public/`.**
   - hPanel → *Advanced → Domains* → your domain → **Change document root**
     → select `public`.
   - If the panel will not let you move it, the alternative is to upload the
     archive's contents *into* `public_html` and add this to
     `public_html/.htaccess` **above** the existing rules:
     ```apache
     RewriteEngine On
     RewriteRule ^(app|bootstrap|config|database|resources|routes|storage|tests|vendor)(/|$) - [F,L]
     ```
     Moving the document root is cleaner and less likely to leak a file.

4. **Run the setup script.** hPanel → *Advanced → SSH Access* (or *Cron Jobs →
   run once) → then:
   ```sh
   cd ~/domains/yourdomain.com/public_html/woodex-v1.0.0   # adjust to your path
   sh deploy.sh
   ```
   No SSH? You can run each step by hand — see section 8.

5. **Edit `.env`.** In File Manager, open `.env` and set at minimum:
   ```ini
   APP_URL=https://yourdomain.com
   PUBLIC_SITE_URL=https://yourdomain.com
   OWNER_EMAIL=you@yourdomain.com
   PUBLIC_LEADS_ALLOWED_ORIGINS=https://yourdomain.com
   MAIL_FROM_ADDRESS="noreply@yourdomain.com"
   ```
   Leave `APP_DEBUG=false`. Never set it to `true` on a public site.

6. **Sign in and change the password.**
   `https://yourdomain.com/admin` → the owner account → then:
   ```sh
   php artisan woodex:owner --password='a-long-new-password'
   ```

7. **Enable HTTPS** in hPanel (free SSL). With `SESSION_SECURE_COOKIE=true`,
   the admin will not stay signed in over plain HTTP — that is deliberate.

---

## 3. cPanel / generic Apache

Same as above. Document root is set under *Domains → Manage → Document Root*.
`mod_rewrite` must be on and `AllowOverride All` must be set for the folder,
otherwise `public/.htaccess` is ignored and every URL except `/` returns 404.

Confirm it took effect: `https://yourdomain.com/shop` should return 200, and
`https://yourdomain.com/architecture` should redirect 301 to `/services`.

---

## 4. VPS / dedicated (Apache)

```sh
sudo apt install php8.4 php8.4-{cli,fpm,sqlite3,mbstring,xml,curl,gd,bcmath} unzip
sudo unzip woodex-v1.0.0.zip -d /var/www/
cd /var/www/woodex-v1.0.0 && sh deploy.sh
sudo chown -R www-data:www-data storage bootstrap/cache
```

Apache vhost:

```apache
<VirtualHost *:443>
    ServerName yourdomain.com
    DocumentRoot /var/www/woodex-v1.0.0/public

    <Directory /var/www/woodex-v1.0.0/public>
        AllowOverride All
        Require all granted
        Options -Indexes
    </Directory>

    ErrorLog  ${APACHE_LOG_DIR}/woodex-error.log
    CustomLog ${APACHE_LOG_DIR}/woodex-access.log combined
</VirtualHost>
```

## 5. Nginx

Nginx ignores `.htaccess`, so the rules that live there must be translated.
This block reproduces them: static pages first, then the app.

```nginx
server {
    listen 443 ssl http2;
    server_name yourdomain.com;
    root /var/www/woodex-v1.0.0/public;
    index index.html index.php;

    charset utf-8;
    client_max_body_size 25m;

    # --- 137 legacy redirects, generated by `website:publish` ---
    # Keep this include in sync: re-run `php artisan website:publish` after
    # adding a redirect in the admin, and regenerate with DEPLOY.md §9.
    include /var/www/woodex-v1.0.0/public/nginx-redirects.conf;

    # robots.txt and theme.css belong to the app, never to a stale file.
    location = /robots.txt { try_files $uri /index.php?$query_string; }
    location = /assets/theme.css { try_files $uri /index.php?$query_string; }

    # The page builder's draft preview must always reach the app.
    if ($args ~ "(^|&)preview=1(&|$)") {
        rewrite ^ /index.php last;
    }

    location / {
        try_files $uri $uri/ $uri/index.html /index.php?$query_string;
    }

    location ~ \.php$ {
        include fastcgi_params;
        fastcgi_pass unix:/run/php/php8.4-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        fastcgi_param DOCUMENT_ROOT $realpath_root;
    }

    location ~ /\.(?!well-known).* { deny all; }
}
```

A ready-made `public/nginx-redirects.conf` ships with this archive — the same
137 rules that are in `.htaccess`, translated from the same map. Regenerate it
after any redirect change:

```sh
php tools/redirects-to-nginx.php
```

It reads `public/redirects.json` (rewritten by **Publish site**) and emits the
`rewrite … permanent;` lines, so the two web servers cannot drift apart.

## 6. Scheduled tasks

Reminders, quote follow-ups, review requests, SLA checks and invoice reminders
are console commands. Add one cron entry — Laravel schedules them internally:

```cron
* * * * * cd /path/to/woodex-v1.0.0 && php artisan schedule:run >> /dev/null 2>&1
```

On Hostinger: hPanel → *Advanced → Cron Jobs* → *Custom*, command above with
your real path, once per minute.

If you use `QUEUE_CONNECTION=database` (the default), also run a worker:

```cron
* * * * * cd /path/to/woodex-v1.0.0 && php artisan queue:work --stop-when-empty >> /dev/null 2>&1
```

## 7. Moving from SQLite to MySQL (recommended for real traffic)

SQLite handles a small site fine, but MySQL is the safer long-term choice.

1. Create a database and user in your panel.
2. In `.env`:
   ```ini
   DB_CONNECTION=mysql
   DB_HOST=127.0.0.1
   DB_PORT=3306
   DB_DATABASE=woodex
   DB_USERNAME=woodex
   DB_PASSWORD=...
   ```
3. Build the schema and the reference data:
   ```sh
   php artisan migrate --force
   php artisan db:seed --class=CatalogSeeder --force
   php artisan db:seed --class=SiteContentSeeder --force
   ```
4. Republish the static pages so `public/` matches the new database:
   ```sh
   php artisan website:publish
   ```
5. Clear the config cache:
   ```sh
   php artisan optimize:clear
   ```

Keep `database/database.sqlite` as your backup — it is the only copy of the
content that shipped with this archive.

## 8. Manual setup (no SSH)

If you cannot run `deploy.sh`, do these steps in File Manager:

1. Copy `.env.example` to `.env`.
2. Generate a key — either paste one from another machine's `php artisan
   key:generate --show`, or run the app once at `/admin/login`; it will refuse
   to start without a key and print what is missing.
3. `chmod` `storage/` and `bootstrap/cache/` to 755 (recursively 775 if your
   host uses group ownership).
4. If images in the admin do not load, create a symlink `public/storage` →
   `../storage/app/public` (File Manager → *Create symlink*).

## 9. After publishing a redirect

`public/.htaccess` contains a generated block:

```
# BEGIN WOODEX REDIRECTS — generated by `website:publish`, edits are lost
```

When you add or change a redirect in the admin (**Website → Redirects**) and
press **Publish site**, that block is rewritten. Nothing else in `.htaccess`
changes. On Nginx, regenerate `nginx-redirects.conf` as shown in section 5.

## 10. Troubleshooting

**500 error, blank page.** Read `storage/logs/laravel.log`. Nine times in ten it
is a missing PHP extension or `storage/` not writable.

**Every URL except `/` is 404.** `mod_rewrite` off, or `AllowOverride None`.
`.htaccess` is being ignored.

**Admin signs in then bounces back to the login page.** `APP_URL` does not match
the address in the browser, or you are on `http://` with
`SESSION_SECURE_COOKIE=true`. Set `APP_URL` to the exact origin you use.

**"No application encryption key has been specified."** `.env` has an empty
`APP_KEY`. Run `php artisan key:generate --force`.

**Images uploaded in the admin show as broken.** The `public/storage` symlink is
missing — `php artisan storage:link`. Some shared hosts block symlinks; in that
case set `FILESYSTEM_DISK=public` and upload into `public/storage` directly.

**The site shows old content after editing.** You edited the CMS but did not
press **Publish site**. The public HTML files are generated; the database alone
changes nothing on the storefront.

**Changed `.env` and nothing happened.** A cached config is pinned:
`php artisan optimize:clear`.

**Robots/sitemap still point at an old domain.** `PUBLIC_SITE_URL` in `.env`,
then `php artisan website:publish`.

## 11. Before you call it live

- [ ] `APP_DEBUG=false`, `APP_ENV=production`
- [ ] Owner password changed from the demo one
- [ ] `APP_URL` / `PUBLIC_SITE_URL` / `PUBLIC_LEADS_ALLOWED_ORIGINS` are the real domain
- [ ] HTTPS on, `SESSION_SECURE_COOKIE=true`
- [ ] `WOODEX_PREVIEW_SHOW_CREDENTIALS=false` and `WOODEX_SYNTHETIC_PREVIEW=false`
- [ ] `MAIL_MAILER` set to a real mailbox — otherwise leads are only in the log
- [ ] `https://yourdomain.com/.env` returns 404
- [ ] Cron running every minute
- [ ] `storage/` and `database/database.sqlite` included in your backup job
- [ ] Test: submit the contact form → the lead appears in `/admin/leads`
